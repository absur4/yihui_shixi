# Zenoh 双机点对点测试结果报告

- 实验 ID：`test01`
- 正式数据目录：`D:\2026-9实习项目\zenoh-multihost-bench-exe\release\zenoh-multihost-bench-windows-x64\results\test01`
- 测试时间：2026-09-17 10:08:16 至 2026-09-17 12:39:10
- 测试规模：30 个工况，150 轮；每工况 5 次重复
- 场景：1 Publisher -> 1 Subscriber，A->B 与 B->A 双方向，TCP / Reliable / Block

## 1. 结论摘要

1. 150/150 轮均执行完成且结构校验有效。结果文件原始判定把 150 轮全部记为 `indeterminate`；按给定规范复核后，109 轮可确定为 `fail`，41 轮仍为 `indeterminate`，形成 20 个 `stable_fail` 和 10 个 `unstable_or_insufficient` 工况，没有 `stable_pass`。
2. 计数诊断显示：计划 972,000 条，实际提交 206,402 条（21.23%），正式窗口收到 205,812 条，收尾截止前收到 206,308 条。主要缺口来自发送端跳过 765,597 个计划时隙，而不是已提交消息的大量网络丢失。
3. 对已提交消息，正式窗口计数交付率为 99.714%，收尾后为 99.954%；仍有 94 条未在截止前交付。30 个工况的最终未交付率中位数均为 0，但 3 轮存在非零最终未交付，最差单轮为 45.833%。
4. B->A 的工况中位吞吐在 12 / 15 个配对工况高于 A->B；A->B 更高 0 个，持平 3 个。方向差异在大载荷下尤其明显。
5. 500 Hz 以上的 8 KiB 工况实际提交速率集中在约 123-128 Hz；64 KiB 高速档约 103-128 Hz。当前结果首先暴露的是发送生成/提交路径达不到目标速率，不能据此认定为 Wi-Fi PHY 或 Zenoh 协议的容量上限。

## 9. 解释边界与建议

- 本结果仅代表当前两台电脑、当前 Wi-Fi 环境、Zenoh TCP/Reliable/Block 与当前 Python 发送实现的组合系统性能，不是 Zenoh 理论上限，也不是 Wi-Fi 上限。
- 高速小包和大载荷条件中，发送达成率随压力显著下降，而已提交消息的窗口交付率多数较高，说明优先优化和剖析发送调度、同步 `publisher.put` 阻塞、内存拷贝及 Python/Windows 调度。
- 下一次要获得正式容量与延迟结论，应先独立验证时钟模型并将窗口不确定度压到 <=20 ms、延迟不确定度压到 <=1 ms；同时补做每方向 TCP 基线和 AP 信息归档。
- 若目标是确认应用可承受的稳定负载，应在修正时钟质量后，对候选边界做更长时间重复；不要直接把本批次吞吐平台写成网络容量。
