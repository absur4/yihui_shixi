VSOA / MQTT / Zenoh 跨设备性能对比试验方案

版本：2.0，综合定稿版

日期：2026-09-16

适用条件：两台固定电脑、同一个 Wi-Fi AP，完成双向端到端业务性能比较。

文档性质：试验设计与统一指标规范。本文没有声称任何测试已经通过，也不以“最终版”表示不存在测量误差。所有实现方按本版本执行；改变主试验条件必须创建新的 experiment_id 和配置版本。

## 1. 试验目标与结论边界

本试验比较指定设备、无线环境、服务配置和部署方式下，中间件完成相同应用层任务时的端到端系统性能。结果包含客户端、必要转发服务、运行时、操作系统和网络的共同影响。

保留四个场景：CD1 消息速率扫描、CD2 载荷扫描、CD3 单远端主机多订阅实例扇出、CD4 持续负载验证。这是三组受控扫描与一组持续性试验，不称为完全正交设计，也不推断所有因素的交互作用。

试验回答：目标负载能否产生、已提交消息能否及时交付、收尾后仍有多少未交付、延迟和资源如何变化，以及在已测范围内哪里出现性能边界。不得将结论扩展为协议理论上限、所有硬件上的排名、Wi-Fi PHY 上限或多接收设备扩展能力。

## 2. 部署、服务语义与比较分组

### 2.1 设备身份与部署

物理设备始终叫 A、B；逻辑角色叫 S（发送端）、R（接收端）。正向为 S=A、R=B，反向为 S=B、R=A。结果同时保留物理身份和逻辑角色，不能在反向试验中重新命名物理机器。

主试验 profile 为 `sender_service_tcp_v2`：必要的 Broker、Router、Server 等独立中间件服务放在 S，R 运行独立订阅者。发现服务与数据转发服务分别注明，不能仅凭组件名字推断数据经过它。

| 对象 | 发送角色 S | 接收角色 R | 需要核实和记录 |
|---|---|---|---|
| VSOA | Publisher，以及实际版本所需的基础服务 | Subscriber | TCP 数据通道、发现和转发路径、缓冲行为。 |
| MQTT | Publisher + Broker | Subscriber | MQTT 版本、发布及订阅 QoS、Broker 队列和会话配置。 |
| Zenoh | Publisher peer；默认不加非必要 Router | Subscriber peer | 显式 TCP 数据路径、reliability、congestion control、发现方式。 |

不添加第三台数据转发电脑。控制器可在 S 运行，或由独立有线控制机承担；控制机不进入被测业务路径。

数据逻辑方向是 S→R，但两台无线终端通常需要经 AP 转发，并不等于只占用一次无线发送。多订阅者可能产生多份无线业务流、协议确认和重传，应按实际抓包或接口统计披露，不能承诺三种架构具有相同空口次数。

接收端部署基础服务可作为独立扩展 profile `receiver_service_tcp_v2`；不得与主 profile 混合求极限或排名。选择发送端作为主 profile 是为了明确 CD3 的远端订阅成本，不表示这一部署普遍优于接收端部署。

### 2.2 主比较语义

主组定义为“持续连接、TCP 数据通道、不增加应用层补发、不进行持久回放的业务基线”。这不等于任意故障下的端到端可靠交付保证。

默认配置：VSOA 使用该版本支持的 TCP 业务模式；MQTT 使用 3.1.1、发布和订阅均 QoS 0、clean session、retain=false、关闭磁盘持久回放；Zenoh 使用显式 TCP、Reliable、Block，并关闭存储回放和应用补发。所有具体配置须在预检中确认生效并归档。

MQTT QoS 0 的底层 TCP 不代表其应用交付语义与其他 Reliable 模式完全等价。报告必须列出接口接受、协议确认、拥塞丢弃和故障恢复语义差异。主组只能称为上述部署条件下的业务基线比较，不能声称严格相同的故障可靠性。

需要严格可靠性对等、Best Effort、QoS 1/2、TLS 或持久恢复比较时，建立单独语义组。无法提供对应语义的实现标记 unsupported，不以相近名称替代。主组不注入网络故障；恢复测试属于独立扩展，不混入 CD1–CD4。

### 2.3 共同工作负载约束

- 每个 Publisher 一个独立进程；CD3 每个 Subscriber 一个独立进程和真实订阅实例。不同进程模型另建 profile。
- 每次发布一个正式逻辑消息，使用相同二进制净荷和固定随机种子；关闭应用压缩与业务批量合并。原生协议分片允许，但须记录；不支持的消息大小不得静默缩小或额外添加应用分片。
- 应用发送器采用固定时刻调度；在可用 API 上使用有界异步提交，不能让未声明的逐条确认等待改变负载模型。只支持阻塞 API 时保留实际行为，明确标记并统计阻塞。
- 公共待提交缓冲最多 1024 条且净荷合计最多 64 MiB，先到达哪个上限就采用哪个；不得另外缓存无限积压。队列满或错过计划时刻的消息记为未提交，不在后续突发补齐。
- 中间件内部队列、socket 缓冲、未确认窗口和溢出策略逐项记录。有能力设置时采用相同条数/字节上限；能力不同则披露实际值，不宣称完全等缓冲公平性。
- 控制、日志、采样和协议确认的字节数不计入净荷吞吐，但其网络和 CPU 成本不能从物理环境中假定消失。

## 3. 环境预检与默认参数

### 3.1 每个试验批次的预检

记录 AP 型号和固件、SSID、BSSID、频段、信道及宽度，A/B 的设备配置、OS、网卡和驱动、位置、RSSI、协商速率、电源模式、软件版本及配置哈希。固定位置与电源策略，关闭非必要下载和同步；不以关闭防火墙代替配置明确端口规则。

先做 60 秒空闲观测，再以相同 A/B 路径和方向做 TCP 网络基线，每方向 30 秒、3 次。网络基线仅用于背景诊断，不作为中间件必达上限，也不与正式业务流同时运行。保留工具、版本、参数和输出。

确认三家能完成低负载身份、长度、CRC、序号及订阅检查，确认各载荷能力、基础服务位置、真实传输和资源采集。控制面优先走独立有线网络；只有 Wi-Fi 时，正式阶段不上传大日志，状态查询最多每秒一次，校准按统一频率执行，记录控制字节数。

信道、BSSID、物理位置或路由变化时结束当前环境块并重新预检；由被测负载引起的信号、速率或 CPU 变化保留为结果，不能事后挑选删除。未知环境干扰保留标签和证据，不自动归因为中间件问题。

### 3.2 冻结的默认值

| 参数 | 默认值或规则 |
|---|---|
| 正式重复 | 每个条件 5 个重复槽位。 |
| CD1–CD3 预热 / 正式 / 收尾 | 5 s / 20 s / 2 s。 |
| CD1 边界确认与精化正式时长 | 60 s，其余阶段同短场景。 |
| CD4 预热 / 正式 / 收尾 | 10 s / 300 s / 5 s。 |
| 预热负载 | 1 KiB、100 Hz，独立 phase，不计入正式消息。 |
| 预热后静置 | 2 s；仍有预热积压则最多延至 5 s，失败须记录，不带入正式阶段。 |
| 每轮冷却 | 20 s，重新建立会话；不以观察到的好坏调整冷却时长。 |
| 连接与就绪超时 | 30 s。 |
| 资源、可读队列采样 | 每 200 ms；覆盖率至少 95%，原始采样间隔一并保存。 |
| 窗口、目标与最终统计 | 正式时长固定；发送结束不自动延长正式窗口。 |
| 目标交付通过门限 | 99%；作用于最差订阅者的保守窗口估计。 |
| 最终未交付门限 | 每个订阅者不超过 0.1%，单独约束收尾后的交付质量。 |
| 单程延迟质量门限 | 全段估计相对时钟不确定度不超过 1 ms，另检查模型有效性。 |
| 正式窗口对齐门限 | 最大对齐不确定度不超过 min(20 ms, 0.1% × T)，边界消息仍按第 5 节做敏感性判断。 |
| 可选延迟 SLO | p95 ≤ 50 ms；只用于单列的 latency_slo_verdict，不冒充所有业务通用要求。 |
| CPU 高负载提示 | 整机平均或任一完整 10 s 桶平均 >85%，仅为提示，不删除结果。 |
| 内存硬停止 | 任一主机被测进程 RSS 合计达到预检物理内存的 50%；记录实际字节限值。 |
| 收尾后进程清理 | 最多 10 s；清理失败记录 timeout，不无限等待。 |

这些门限是本试验的固定工程判据，不是行业通用标准。团队若采用其他门限，应在开始前生成不同配置版本；不得在看到结果后更换门限并覆盖原结论。

## 4. 场景矩阵与执行计划

### 4.1 CD1：速率饱和扫描

1 Publisher@S → 1 Subscriber@R，净荷 1 KiB，速率为 100、500、1000、2000、5000、10000 Hz；每档正式 20 s、5 次。

粗扫结果保留作为共同绝对负载比较。候选最高通过档和最低失败档分别追加 60 s、5 次确认，以确认结果建立边界。若确认与粗扫矛盾，不直接使用粗扫极限，按第 8 节记录区间不确定性。

若存在可信的通过/失败区间，可追加最多 3 个二分候选速率，每候选 60 s、5 次。整数候选为 floor((R_pass+R_fail)/2)，与已有档重复则停止；当 R_fail/R_pass ≤ 1.10 或达到候选数上限时停止。全部原始档通过时，可按固定序列追加 20000、40000 Hz 的确认测试；仍通过则报告上界未达到。最低档失败时按 50、10 Hz 追加确认；仍失败则报告未找到通过档。追加数据单列，不充当三家共同原始六档。

每档记录目标速率、实际提交速率、三类达成率、正式/最终交付、延迟、阻塞、积压和各端资源。最高原始档仅要求 81.92 Mbit/s 净荷，不保证一定达到网络或系统上限。

### 4.2 CD2：载荷扫描

1 Publisher@S → 1 Subscriber@R，200 Hz，每档正式 20 s、5 次。

| 净荷 | 目标发送净荷吞吐，Mbit/s |
|---|---|
| 1 KiB | 1.6384 |
| 16 KiB | 26.2144 |
| 64 KiB | 104.8576 |
| 256 KiB | 419.4304 |
| 1024 KiB | 1677.7216 |

大载荷用于探测拥塞及过载行为，不要求必达。能力不支持记 unsupported，已支持但运行超时或失败按实际结果记录，不降载重命名为原条件。

出现疑似平台时，构成候选平台的最多三个连续载荷档各追加 60 s、5 次确认。报告该部署的吞吐平台或下降，不将 CPU、运行时、缓冲限制自动归为 Wi-Fi 带宽。

### 4.3 CD3：单远端主机多订阅实例扇出

1 Publisher@S → P Subscribers@R，P=1、2、4；1 KiB、1000 Hz，每档正式 20 s、5 次。每个 Subscriber 独立进程，实际接收并校验消息。

输出每订阅者的交付、延迟和资源，最差订阅者的目标达成率，以及累计净荷吞吐和基础服务资源。累计接收是业务副本交付总量，不是独立物理链路容量。

如果 1000 Hz 已超过某家的 CD1 能力，保留该压力结果；可另建共同低负载扩展组，但不能替换原档或与原档合并。CD3 不称为多设备扇出，也不能承诺扇出不会增加无线流量。

### 4.4 CD4：共同负载、相对稳定负载与压力维持

两方向 CD1 边界确认完成后，为每个中间件、每个方向生成下列三个条件。均为 1 Publisher、1 Subscriber、1 KiB，正式 300 s，10 s 桶、5 次。

| 条件 | 速率规则 | 解释 |
|---|---|---|
| CD4-C 共同负载 | floor(0.8 × 所有三家两方向有效 R_pass 的最小值)，最低 1 Hz。 | 相同绝对负载下比较延迟和资源效率。 |
| CD4-L 相对稳定负载 | floor(0.9 × 本家本方向 R_pass)，最低 1 Hz。 | 在本次已验证容量附近观察持续性。 |
| CD4-H 压力负载 | 有 R_fail 时 ceil(1.2 × R_fail)。 | 观察预计过载下的降速、积压和资源行为。 |

若没有 R_fail，CD4-H 使用已测最高速率并标记 high_load_only，不能声称已构成过载。若没有 R_pass，相关 CD4-L 不生成；无法得到六个有效 R_pass 时，三家完整共同负载组记 not_tested，部分参与者的扩展组另列。

不同家采用的相对速率通常不同，CD4-L/H 不能直接用绝对延迟和 CPU 数字判定谁更高效。即使 C 与 L 数值碰巧相同，仍保留预定重复和条件身份，不偷偷复用运行。

### 4.5 工作量

核心矩阵为 6+5+3+3=17 个条件；每个中间件每方向 85 轮，三家双方向共 510 轮。

每个中间件每方向纯正式测量为 6×20×5 + 5×20×5 + 3×20×5 + 3×300×5 = 5900 s；三家双方向合计 35400 s，即 9 小时 50 分钟。

上述时长不包含预检、预热、静置、校准、收尾、冷却、确认、二分和允许的无效轮补测。按默认阶段执行，核心部分还需数小时附加时间，应分环境块排期。未满足生成条件的项目保留为未测，不伪造 510 轮完成记录。

## 5. 单轮流程、消息身份与计量边界

### 5.1 运行流程

控制器下发不可变 spec → 各端启动并确认真实订阅就绪 → 预热 → 清空预热积压 → 校准并预告正式开始 → 正式测量 → 收尾 → 封存日志和最终校准 → 清理 → 冷却。

正式开始至少提前 2 s 下发，各端确认 armed；未全部确认则不开始正式发送。每端使用本地单调时钟启动固定时长窗口，不使用收到一条 START 数据消息的瞬间作为隐含时间零点。

R 在正式窗口前开始记录，并保留收尾截止后至少 1 s 的诊断接收记录；截止后的消息仅用于解释晚到，不能回填已冻结的最终交付指标。控制流与数据流使用不同通道或主题，并且全部标识 run_id 和 phase。

### 5.2 共同消息格式

测试元数据采用共同的 64 字节二进制头，网络字节序：magic 4、version 1、phase 1、flags 2、run UUID 16、publisher_id 4、sequence 8、send_monotonic_ns 8、payload_length 4、payload_crc32 4、reserved 12 字节。其后恰好为 S 字节净荷。

净荷由相同种子生成，预生成和 CRC 计算置于计时之外；发送时间在进入发送 API 前立即记录。接收时间在应用接收回调入口、解码和 CRC 校验前记录。因此延迟包含中间件 API、排队、网络、转发和接收调度，不是纯网络时延。

唯一消息键为 (run_id,publisher_id,sequence)，唯一交付键再增加 subscriber_id。只对本轮、正式 phase、来源匹配、长度和 CRC 正确的消息计入有效交付。去重取第一次有效接收；重复、损坏、外来消息、不可解析消息分别计数。

### 5.3 调度与提交计数

本方案速率均取正整数，时长为整秒，每发布者计划序列为 k=0…R_cfg×T−1，计划时刻为 t0+k/R_cfg。正式发送区间左闭右开 [t0,t0+T)。跳过的时隙保留为未尝试/未提交，不以补发改变目标时序。

N_planned=R_cfg×T×N_pub；N_attempt 为在正式阶段首次调用发送 API 的唯一消息数；N_sent 为该批尝试中被中间件发送接口接受、且在收尾截止前可确认接受状态的唯一消息数。API 接受不等于已上网、协议确认或订阅端收到。

发送尝试的返回值、调用开始/结束、入队/接受证据及可用的协议确认分别保存。调用在正式阶段开始、收尾期才返回接受时，仍属于正式发送批次，另记 late_accept_count；不得在正式结束后新建正式发送尝试。

N_sent/T 是固定窗口所启动的成功提交批次速率，不称为物理网络发送速率。接收匹配可以离线等待源日志封存，但不能仅凭接收数反推“发送成功”。接受结果无法确定时记录 submission_unknown_count，相关交付分母标不可测，该轮不能获得容量通过结论。

### 5.4 正式、收尾和边界敏感性

S 与 R 均记录实际本地正式起止时间；R 的固定窗口为 [b0,b0+T)，最终截止为 b0+T+D。N_recv_win 是本轮有效唯一交付在 R 正式窗口内的累计数量；N_recv_final 是同一批消息在最终截止前的累计数量。控制日志、额外观察和收尾不增加 N_planned。

Mbit/s 的主分母固定为 T，不使用首末成功发送或跨设备首末交付跨度。资源窗口和本地到达吞吐也使用本地正式窗口。跨设备校准主要用于延迟、窗口相对对齐和按源批次的时间分析。

窗口不确定度 u_window 包含起止偏移估计、运行期漂移、计时分辨率和实际启动误差。只有在第 3 节门限内，窗口达成率才可参加共同容量判定。校准不满足 1 ms 但仍满足较宽的窗口门限时，可以仅将单程延迟作废。

对每条链路，Q 为在正式起点或终点各 ±u_window 区间内的本轮有效唯一交付数（含前后诊断记录，集合去重）。令 M=N_recv_win_j、E_j=N_sent，则 M_lower=max(0,M−Q)，M_upper=min(E_j,M+Q)。容量判断使用由这两个数产生的目标达成率区间，不把边界敏感样本强判为通过或失败。

如果窗口偏移上界未知或超限，本地计时吞吐仍可保存为诊断，但不能与对齐合格轮次直接排名；目标窗口、源批次桶和同步总资源标记不可比。最终计数可以保留为“R 本地截止规则下”的交付结果，注明截止对齐限制，不能声称同一物理期限已被验证。

## 6. 统一指标定义

全部比率用 0–1，页面展示时才乘 100；吞吐用十进制 Mbit/s，内存用 RSS/1e6 MB，时间戳 ns，延迟 ms，窗口 s。每项数值同时有质量标记；不可测填 null 并说明原因，不以字符串或 0 冒充有效数值。

### 6.1 发送、吞吐与交付

令 E=N_sent×P，E_plan=N_planned×P。N_recv_win/final 是按完整交付键去重后的累计有效数量。

| 字段 | 定义 |
|---|---|
| actual_publish_rate_hz | N_sent/T；多发布者另给每发布者值，当前 CD1–CD4 均 N_pub=1。 |
| target_offered_throughput_mbps | N_planned×S×8/T/1e6；发送端目标净荷吞吐。 |
| offered_throughput_mbps | N_sent×S×8/T/1e6；实际提交批次的净荷吞吐，不乘 P。 |
| target_delivery_throughput_mbps | E_plan×S×8/T/1e6；全部预期业务副本的目标吞吐。 |
| offered_delivery_throughput_mbps | E×S×8/T/1e6；已提交消息对应的全部副本吞吐。 |
| throughput_mbps | N_recv_win×S×8/T/1e6；R 正式窗口内累计有效净荷吞吐。 |
| send_achievement_ratio | N_sent/N_planned；发布负载达成率。 |
| delivery_achievement_ratio | N_recv_win/E；已提交消息的窗口交付达成率。 |
| end_to_end_achievement_ratio | N_recv_win/E_plan；目标交付达成率，主容量指标。 |
| window_missing_ratio | 1−N_recv_win/E；窗口结束仍未交付的比例。 |
| final_missing_ratio | 1−N_recv_final/E；固定收尾截止前最终未交付比例。 |
| drain_delivery_ratio | (N_recv_final−N_recv_win)/E；仅在收尾期补齐的交付比例。 |
| final_target_achievement_ratio | N_recv_final/E_plan；收尾后相对计划目标的完成比例。 |分母非零时，end_to_end_achievement_ratio = send_achievement_ratio × delivery_achievement_ratio；不能改成二者 min。窗口未交付率 = 最终未交付率 + 收尾交付比例。

N_planned>0 且 N_sent=0 时，发送达成率与目标达成率为 0；以 E 为分母的指标为 null；无接收但计数日志完整时吞吐为 0。不得因此报告“零丢失”。N_sent>0 而没有收到消息时，最终未交付率为 1，延迟为 null。

正式结果必须满足 0≤N_recv_win≤N_recv_final≤E、N_sent≤N_attempt≤N_planned。超范围意味着计数、身份或结果不确定性问题，保留错误，不静默裁剪；只有第 5 节的敏感性区间按定义截断。

现有接口若需要旧字段，兼容导出 packet_loss=window_missing_ratio、final_packet_loss=final_missing_ratio，并声明 metric_definition_version=2.0。其他旧别名必须列入映射表；不得把 1.0 与 2.0 结果混合。

### 6.2 延迟、分位数和抖动

单程延迟 d_i=(a_i_corrected−s_i)/1e6。主延迟样本来自正式发送且在正式窗口首次有效到达的消息；收尾消息不进入主延迟，另输出 latency_final 系列以揭示晚到样本，数据集身份不能混淆。

| 指标 | 算法 |
|---|---|
| latency_ms | 有效主样本的算术平均。 |
| latency_p50_ms / p95 / p99 | 排序 x；h=(n−1)k，lo=floor(h)，hi=ceil(h)；x[lo]+(x[hi]−x[lo])×(h−lo)，k=0.50/0.95/0.99。 |
| latency_std_ms | 总体标准差，ddof=0。 |
| jitter_ms | 同一 publisher→subscriber 链路中序号恰好相差 1 的有效主样本延迟差绝对值的均值；不跨缺号、不跨 phase、不跨链路。 |

同时报告每链路样本数和 jitter_sample_count。累计延迟可以合并同一轮各链路样本，但必须保留逐链路和最差链路；累计抖动按有效样本对数量加权，不能随意平均不同样本量的链路均值。

计算函数对 n>0 可给出分位数诊断值。正式比较默认 p50 至少 20 个、p95 至少 200 个、p99 至少 1000 个有效样本；不足时相应比较字段为 null，诊断值可另存。门限只是最小样本规则，不保证特定置信区间。

所有延迟图必须附交付率、样本覆盖率和时钟质量。大量未交付时，收到的快消息可能使 p99 看起来降低，不能据此评为更好。不得将缺失消息的未知延迟填成 0，也不得插值生成接收样本。

### 6.3 资源、阻塞与积压

按进程、角色、物理设备保存 CPU 累计时间、RSS、时间戳及采样间隔。进程 CPU=CPU 时间增量/墙钟间隔×100%，一逻辑核满载为 100%；均值按采样间隔与正式窗口重叠加权。整机 CPU 使用 OS 的 0–100% 口径，分别报告，不直接跨机器相加。

中间件资源包括 Publisher、Subscriber 与必要基础服务；Agent、独立日志压缩和报告进程单列。不可分离地运行在端点内的测试回调和日志开销保留在端点资源中，声明范围，不凭估算扣除。

每机和每角色 RSS 峰值按本地正式窗口计算。同一时刻总 RSS 峰值须用对齐后的共同 200 ms 网格求和再取最大值，使用最近的过去样本且样本年龄不超过 400 ms；有效网格覆盖至少 95%。不可对齐时只提供各机峰值与 peak_sum_mb，不能把峰值之和命名为同时总峰值。

发送 API 耗时记录总量、p95、最大值；API 调用耗时不自动等于队列阻塞，能分辨时另记 blocked_time。队列深度按可观察层级分列，不把一个内部队列当作端到端总积压。

时钟和日志允许时，按源发送批次计算“截至 t 已提交但未有效交付”的数量；它包括丢失和在途消息，不称为实测队列深度。观测不到内部队列时填 null，但可用收尾补齐、窗口内及时交付及该未完成数量解释积压。

## 7. 跨设备校准、窗口质量与降级

### 7.1 校准协议

S 的单调时钟为参考，R 为待映射时钟。每次交换保存 S 发送 t1、R 接收 t2、R 回复 t3、S 接收 t4，均为各机原始单调 ns；不得只保留一个 RTT。

在一次交换内时钟速率近似不变的条件下，网络往返估计 r=(t4−t1)−(t3−t2)，R−S 偏移估计 theta=((t2−t1)+(t3−t4))/2。负 r、乱序时间戳、时钟跳变或进程休眠导致的异常交换作废并保留原因。

每轮正式前后各至少 9 次交换；正式过程中每 5 s 一组、每组 9 次。所有中间件使用相同校准大小、周期和控制通道。主业务停止后继续校准覆盖收尾终点；每个校准段至少 5 次有效交换，否则该段无有效校准。

最小有效 r 对应的 theta 可作为偏移中心估计；r/2 仅在非负单向时延及短时速率稳定等假设下给出该观测时刻的区间尺度，不能证明运行全程的误差上限。使用直接 S↔R 校准时不再叠加两个经第三控制器得到的 RTT/2。

### 7.2 运行期模型和质量条件

用相邻校准中心分段线性映射 R 时间到 S 时间，映射必须连续且单调。保存每个校准中心、原始交换、校准区间和拟合残差，禁止仅用 300 秒起止两点插值后宣称全程可靠。

每段的不确定度模型为 u_segment=max(u_left,u_right)+timestamp_error+model_error。model_error 必须包含未被观测解释的时钟速率变化；可用事先验证的相对漂移上界 rho_max 和校准间隔构造保守项，例如 rho_max×interval/2，并加验证残差。必须记录估计方法及其假设。

不能获得可信的模型误差估计时标 model_unvalidated，不用未经验证的默认 ppm 数字假装物理误差保证。此时仍保存本地计时、计数和 RTT 诊断，单程延迟不作有效排名。实际精度可能使 Wi-Fi 下部分或全部单程延迟不可测，这是合规结果。

每个主延迟样本及其所在段需满足 u_segment≤1 ms。只有主样本所涉及校准段全部合格，才发布整轮主延迟点估计；部分覆盖时只输出明确标注的分段诊断，避免仅挑好时段。

负校正延迟不得截成 0。若小于负误差界，记 clock_consistency_failed；即使落在误差范围内，相关链路/桶的延迟点估计仍标不可测并保留原始值与区间，不能删除这些样本后继续声称全样本结果。

clock_drift_ms=theta_end−theta_start；它是偏移变化，不是每秒漂移率。比较两家微小延迟差异时，应同时考虑两者时钟不确定度与重复间波动，不用差异小于误差范围的数据宣布胜负。

### 7.3 两级降级

延迟门限不合格但窗口对齐合格：保留容量、计数、固定窗口吞吐和本地资源，单程延迟及其拐点不可测。

窗口对齐也不合格：保留各端本地时间定义的吞吐、计数和资源诊断；共同窗口达成率不能用于 R_pass/R_fail，跨设备同步资源和源批次分桶不可测。不能笼统声称任何时钟问题都不影响容量结论。

可以在独立条件中测试应用层回显 RTT，发送和回显到达均在 S 计时；控制校准 RTT 与业务 RTT 分开命名。回显会增加业务流量，不与原单向吞吐轮次混合，也不以 RTT/2 替代单程延迟。

## 8. 有效性、容量边界与瓶颈判定

### 8.1 执行状态与指标质量

execution_status 使用 completed、error、timeout、cancelled、unsupported、not_tested；metric_quality 分项使用 valid、unmeasurable、insufficient_samples、incomplete。run_validity 可为 valid、partial、invalid，不能因单程延迟不可测就删除整轮。

被测进程在规定负载下崩溃、超时、触及资源限值或发送失败，是该部署的运行失败，应计入容量失败证据，即使部分数值缺失；缺失数值不补零。独立采集器损坏、错误配置或实验外部断电属于无效/中断，需要证据，不自动当作容量失败或可删除的坏样本。

有效容量数据需要源/接收日志完整、计数不变量成立、实际 profile 匹配、窗口对齐合格。资源覆盖不足只使资源指标无效，不抹去完整交付结果；使用资源硬限值作为失败原因时须有对应证据。

### 8.2 单轮与条件通过规则

每个订阅者 j 的计划交付分母为 N_planned。单轮容量通过须同时满足：窗口质量合格、目标达成率保守下界 min_j(M_lower_j/N_planned)≥0.99、每链路 final_missing_ratio≤0.001、没有运行失败或计数未知。

任何一条链路的目标达成率乐观上界仍 <0.99，或最终未交付门限不合格，或出现被测系统运行失败，则该轮容量失败。边界区间跨门限时为 indeterminate，不强行二分。

latency_slo_verdict 单独判断 p95 与预设 50 ms 门限；证据不足为 unmeasurable。容量通过不意味着延迟 SLO 通过，完整报告须同时列出两项。积压增长作为持续性判据在第 9 节报告，不用不透明的总分抵消交付不足。同一条件 5 个重复槽位中至少 4 个容量通过，为 stable_pass；至少 4 个容量失败，为 stable_fail；其他为 unstable_or_insufficient。中位数用于描述，不能替代这个规则。

仅对有证据的实验设施无效轮允许每槽位最多补测一次，保留原 run_id 和替代关系，采用第一份有效补测结果。被测系统失败不补成成功；不得反复运行直到凑齐五次好结果。

### 8.3 R_pass、R_fail 和延迟拐点

在已确认档位中，如果通过档均低于失败档且无未解决的不稳定间隙，R_pass 为最高 stable_pass，R_fail 为高于它的最低 stable_fail。报告观察到的区间和精化宽度，不把首次失败值称为精确物理极限。

保留兼容名 R_sustainable=R_pass、R_sat=R_fail，并声明前者只是规定短时条件下的容量通过档，不是无限期稳定速率。所有确认档通过则 R_fail=null、bound_status=not_reached；未找到通过档则 R_pass=null、bound_status=below_range。

存在较低失败但较高通过、或精化档不稳定时，bound_status=non_monotonic_or_uncertain，不给出确定饱和区间。共同低负载可以使用低于全部问题档的已确认通过速率，但须标注来源；无法得到可信参考则不生成相对极限条件。

R_knee 基线固定为同家同方向 CD1 的 100 Hz 条件，使用至少 4 轮可测 p95 的中位数。后续连续两个已测更高速率档的 p95 中位数均超过其 3 倍，前者记为实测拐点候选。仅最后一档越线为 candidate；基线或样本不足则不可测。不得使用所有档中的最小值作为事后基线。

### 8.4 CD2 平台

对载荷递增后的接收吞吐中位数 G0、G1、G2，只有 G0、G1>0，且两段相对变化绝对值均≤5%，才构成三个点的平台候选。显著下降标记 collapse，不把负增长误当“增幅小于 5%”的平台。

候选高负载档还需至少 4/5 轮目标达成率失败，或有至少 4/5 轮发送阻塞/可观测积压增长证据。按第 4 节长窗口确认仍满足时，B_plateau=(G0+G1+G2)/3，保留三个分量；否则仅为 candidate。

没有三个支持的有效档、没有确认、或者所有目标负载均达到时，平台字段为 null 并说明状态。B_plateau 是该部署的有效业务吞吐平台，网络受限只有在网络基线、接口利用率及两端资源等证据一致时才可标为 supported，其余使用 suspected 或 unknown。

## 9. CD4 分桶、持续性和趋势

### 9.1 到达桶与源批次桶分开

到达桶按 R 本地窗口每 10 s 划分，计算该桶首次有效到达数和净荷吞吐。旧积压集中释放可能使某桶瞬时吞吐超过目标，这不等于该桶新消息达成，不能裁剪成 100%。

源批次桶按 S 正式发送时刻和计划序列分为 30 组。第 k 桶的计划数、实际提交数仅来自该组；及时交付数仅统计该组中在对应桶结束前有效到达的消息。不能用上一桶的晚到消息抵消当前桶未交付。

每组的最终交付在整轮固定收尾截止后回填并标 finalized=true；因此这些“最终”桶具有不同观察余量，不用于比较等时限恢复能力。正式图同时给出到达吞吐、源批次目标达成、收尾补齐和未完成数量。

源批次桶和跨端未完成数量要求可用的窗口映射与边界敏感性分析；不满足时仅保留本地到达桶，T_hold 等共同桶判据不可测。边界计算按每个桶末端的不确定度进行，不能只校验整轮起止。

### 9.2 连续维持与退化

桶的容量合格条件为最差订阅者该源批次目标达成率的保守下界≥99%，且该桶无运行失败、源计数未知或窗口质量问题。桶最终未交付另列；整轮最终未交付仍需满足 0.1% 门限。

| 指标 | 定义 |
|---|---|
| T_hold_s | 从第一个桶开始连续合格的完整桶时长；首个失败停止计时。 |
| max_contiguous_stable_duration_s | 整轮任意位置最长连续合格桶时长，不与 T_hold 混用。 |
| hold_censored | 全部 30 桶合格时为 true，报告 T_hold≥300 s。 |
| degradation_delta_pp | 100×(后 10 桶目标达成率均值−前 10 桶均值)。 |
| degradation_slope_pp_per_min | 以桶中心时间的分钟数为横轴，对 100×目标达成率作普通最小二乘回归。 |
| latency_p95_slope_ms_per_min | 源批次可测 p95 对桶中心时间回归。 |
| memory_growth_slope_mb_per_min | 各机 RSS 桶峰值对桶中心时间回归。 |
| backlog_growth_deliveries | 最后 10 桶与最前 10 桶结束时未完成交付数均值之差。 |

存在质量未知桶时，记录已验证前缀及 hold_status=indeterminate，不把未知当失败也不跨过去继续宣称连续稳定。趋势指标只有所需桶均完整时发布主结果，部分覆盖的拟合仅为诊断，不填补样本。

本试验“300 秒容量持续通过”要求全部桶容量合格、整轮最终交付合格且未完成交付增长不超过 max(10,0.001×E)。无法重建未完成量时，该持续性结论为 partial，不能以不可见队列默认无积压。延迟 SLO、内存增长趋势单独报告。

所有稳定结论只适用于已观测 300 秒；需要长时间可靠性结论时增加独立的 30–60 分钟扩展条件，不把 5 分钟试验改称长期保证。

## 10. 执行顺序与统计方法

先完成预检和两方向共同粗扫，再做边界确认/精化，之后生成 CD4。使用固定并保存的随机种子，例如 20260916；实际执行顺序必须归档。

以方向、场景、档位和重复槽位构成时间块，在块内随机排列三家中间件，避免先跑完一家再跑另一家。方向顺序跨块交替或随机化；设备位置不变，基础服务随逻辑 S 移动。方向变化后确认配置、连接及校准，避免固定“先正向后反向”混入整日环境变化。

各轮重新建立会话、清理旧队列和旧 phase 状态；不删源数据。确认测试与原始扫描使用不同 condition_id，不因参数接近而合并。

每条件保存 5 个槽位的原始指标、状态和质量。对可测数值先算每轮值，再报中位数、min、max、极差和有效轮数；不足 4 个可测轮时不发布主比较汇总。不能将五轮样本混池后重新计算 p95/p99，不能把 30 个桶当 30 次独立重复。

失败比例必须与数值汇总同表显示。不同可靠性、部署、方向或窗口质量的数据分表；两方向可给出明确标注的等权方向摘要，但不产生一个隐藏方向差异的总排名。

五轮中位数和极差用于描述，不支持自动宣称统计显著。若需显著性结论，预先设计增加重复数、配对分析、置信区间和多重比较校正；不在看到结果后选择统计方法。

## 12. 公式与边界校验样例

以下为算法验收输入，不是真实性能数据。三家必须在同一组样例上给出一致结果；可共用中立计算模块，也可独立实现后做 golden-data 校验，不能以任一现有模块的行为覆盖本文定义。

表中 T=20 s、S=1024 byte，不考虑时钟边界不确定度；吞吐均为累计业务净荷。

| 情形 | N_planned / N_sent / P | 窗口 / 最终接收 | 发送 / 交付 / 目标达成 | 最终未交付 / 收尾比例 | 吞吐 Mbit/s |
|---|---|---|---|---|---|
| 四订阅者全部送达 | 20000 / 20000 / 4 | 80000 / 80000 | 1 / 1 / 1 | 0 / 0 | 32.768 |
| 发送不足但全部交付 | 20000 / 14000 / 1 | 14000 / 14000 | 0.7 / 1 / 0.7 | 0 / 0 | 5.7344 |
| 发送与交付均 99% | 20000 / 19800 / 1 | 19602 / 19800 | 0.99 / 0.99 / 0.9801 | 0 / 0.01 | 8.0289792 |
| 窗口晚到、最终补齐 | 20000 / 20000 / 1 | 19800 / 20000 | 1 / 0.99 / 0.99 | 0 / 0.01 | 8.11008 |
| 有发送、没有接收 | 20000 / 20000 / 1 | 0 / 0 | 1 / 0 / 0 | 1 / 0 | 0 |
| 完全没有提交 | 20000 / 0 / 1 | 0 / 0 | 0 / null / 0 | null / null | 0 |

四订阅者全部送达案例的 offered_throughput_mbps 为 8.192，offered_delivery_throughput_mbps 为 32.768。不能把累计接收/单份发送所得的 4 当作 400% 目标达成。

额外校验：

1. 原始延迟 [1,2,3,4] ms，线性插值 p95=3.85、p99=3.97，总体标准差约 1.11803398875；这只验证算法，正式样本量质量门限仍需执行。
2. 序列 0、2、3，延迟分别 1、10、12 ms，抖动只取 2→3，结果为 2 ms，样本对数为 1。
3. 重复接收不增加唯一交付；另一订阅者收到同一消息增加独立交付；跳过的发送计划不能误判为已提交消息丢失。
4. 达成率区间为 [0.9895,0.9905] 时判 indeterminate，而非按点估计强判通过。
5. 桶达成率前三个为 1、1、0.98，后续恢复时，T_hold=20 s；最长连续时长另算。全部桶合格只能报告至少 300 s。
6. 前 10 桶均值 0.998、后 10 桶 0.973，变化为 −2.5 个百分点；不能输出 −0.025 pp，也不能把该差值叫斜率。
7. 两台机器各自峰值发生在不同时间时，峰值之和与同步总峰值必须不同名；缺采样或时钟失败不能默认补零。
8. 正式窗口、收尾截止、负校正延迟、零分母、无样本、时钟模型未知和被测系统崩溃，均须有可追溯的质量或失败输出。

## 13. 实施验收与报告措辞

开始正式试验前：所有 profile 配置完成预检；消息格式与计量边界一致；校准、窗口敏感性和异常样例验证通过；每家每方向完成一轮低负载连通性检查；资源范围与控制流量已归档。

执行器应能生成 CD1–CD4 和三个 CD4 子条件、管理两端、保存部分结果并清理子进程。采用统一控制台时，页面明确区分发送/接收节点、物理方向、执行状态与指标质量。UI 接入不替代测量正确性验收。

结束后：五次槽位及补测关系完整、失败未被删除、原始数据能重算、边界与平台包含证据、无结果的场景明确未测。原始 S01–S12 与跨设备 CD1–CD4 使用不同场景命名空间，不能直接覆盖既有同名字段的统计口径。

推荐结论格式：“在某设备、某无线环境、某 profile 和方向下，某配置在规定时长的五次重复中有几次达到既定目标交付与最终交付门限；已确认通过档为多少，失败档为多少；延迟可测性、资源瓶颈和 300 秒持续性结果分别为何。”

避免使用“绝对最高速率”“零丢失保证”“普遍最快”“已达到 Wi-Fi 物理上限”等超出证据的表述。没有获得有效单程延迟或饱和上界也是正常试验结果，不以推算值补齐。

| 输入建议或冲突 | 最终处理与原因 |
|---|---|
| 原方案的 CD1–CD4 与统一净荷口径 | 保留，补充测量边界、方向复测和共同负载。 |
| CROSS_DEVICE_BENCHMARK_PLAN 将服务放接收端，结果评价将服务放发送端 | 主组固定发送角色 S；接收端部署作为独立扩展，避免 CD3 数据路径被不透明地混合。 |
| “可靠传输”标签与具体配置并不完全对等 | 主组精确定义为 TCP 持续连接业务基线，列明语义差异；严格对等与可靠恢复另组。 |
| 吞吐仍采用 T_send / T_delivery | 主字段全部改为固定 T；首末跨度只可作额外诊断，不参与主达成率。 |
| 两吞吐相除、交付比值、min(send,delivery) 三种达成定义 | 分别保留发送、交付和目标达成；目标达成采用计划交付计数分母，等于前两者乘积，不取 min。 |
| packet_loss 在不同文件中表示窗口或最终丢失 | 主规范使用 window_missing_ratio / final_missing_ratio；旧字段仅按显式 2.0 映射导出。 |
| 起止 min RTT 与线性插值被当作充分校准 | 增加运行期校准、模型误差、窗口对齐和分项降级；不虚构 1 ms 精度。 |
| 0.9×首次失败档与 0.9×通过档冲突 | 相对稳定档采用已确认 R_pass；CD4 增加共同绝对负载。 |
| CPU >85% 删除与保留冲突 | 保留结果，用整机高负载提示及逐角色证据解释，不筛掉真实瓶颈。 |
| T_hold 是起始前缀还是任意最长段 | T_hold 取起始连续合格时长；任意最长段另设字段，完整观测按右截断报告。 |
| 总内存直接相加峰值 | 区分同步总峰值与各机峰值之和。 |
| 5 次重复、角色互换、控制隔离、随机化和完整归档 | 采纳，补充无效轮补测上限和被测系统失败处理。 |
