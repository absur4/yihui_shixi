# 二、应用背景

## 第 2 页 · 应用背景：四种中间件的主流应用场所

四者并非同类替代品，而是**为不同场景设计**的通信框架，这决定了各自的技术取舍。

| | 起源 | 主流应用场所 |
|---|---|---|
| **VSOA** | 面向实时嵌入式系统的微服务框架 | 航空电子与国防嵌入式系统、工业自动化与运动控制、车载电子、机器人控制 |
| **MQTT** | 为低带宽、不可靠链路设计的轻量协议 | 物联网（IoT）、工业物联网、智能家居、远程设备遥测与监控（电力、水务、环保）、移动推送 |
| **Zenoh** | 新一代 pub/sub，主打去中心与广域适配 | 机器人（ROS 2 / 自动驾驶）、边缘计算、车路协同、大规模分布式传感网 |
| **DDS** | OMG 标准的以数据为中心（DCPS）中间件 | 航空航天与国防、自动驾驶 / ADAS、工业自动化、医疗设备、电力能源、金融交易 |

**各自的设计侧重**
- **VSOA**：强实时、资源受限；微服务 + 发布订阅 + RPC 一体；小包高频的控制与状态回传
- **MQTT**：海量设备接入、弱网跨 NAT、低带宽；broker 中心化中继换取极简的终端实现；QoS 分级可靠性
- **Zenoh**：无中心、P2P 直连、跨局域网到广域的统一抽象；高吞吐与低延迟兼顾；动态拓扑
- **DDS**：以数据为中心，QoS 维度最丰富（可靠性 / 持久性 / 截止期限 / 生命周期）；自动发现；确定性实时；大规模节点

## 第 3 页 · 从应用场所推导评价维度

应用场所 → 负载特征 → 测试维度，逐层对应：

| 应用场所的共性需求 | 负载特征 | 测试维度 |
|---|---|---|
| 控制指令、状态回传（VSOA / DDS 的主战场） | 小包、稳定的高频发送 | **发送速率** |
| 图像 / 点云 / 配置下发（DDS / Zenoh 常见） | 单条消息体积跨度大 | **消息尺寸** |
| 多传感器汇聚、多订阅者分发（MQTT / DDS 常见） | 端数变化 | **拓扑规模** |
| 车机 / 工业现场需长期连续运行 | 持续负载 | **时间（长稳）** |

**由此确定的四个正交压力方向**：速率（条/s）、尺寸（bytes/条）、拓扑（端数）、时间（持续）。
后文的全部实测数据，都落在这四个方向上。

# 三、原理

## 第 4 页 · 原理（1）VSOA

- 定位：原生微服务 / 发布订阅框架，自带服务注册（**Position** 服务）与 JSON-RPC 风格调用
- 传输：TCP / UDP 双模；本次测试用 TCP
- 关键机制：**应用层分片** —— `fragment_size_bytes = 60000`
  - 发布端按 60000 B 切片，订阅端按 `fragment_index / fragment_count` 重组
  - 64 KiB → 2 片；1 MiB → **18 片**
- 时钟：单调时钟 `perf_counter_ns`；跨机时用最小 RTT 法标定偏移
- 对性能的影响：整包延迟取决于**最慢的一片**，片数越多尾部越容易被拉长

## 第 5 页 · 原理（2）MQTT

- 定位：轻量级发布订阅，**以 broker 为中心**：发布端 → broker → 订阅端，**两跳**
- 传输：TCP；QoS 0/1/2（本次 qos1，`clean_session=False`，`max_inflight=20`）
- 关键机制：broker 单点转发 + 会话与重传；发布端与订阅端各自独立进程
- 对性能的影响：
  - 一跳转发带来固定的延迟增量
  - 大消息时 broker 需**完整接收再转发** → 多一次内存拷贝与排队，尾部代价最明显
  - 扇出时所有订阅者共享 broker 单点，成本集中

## 第 6 页 · 原理（3）Zenoh

- 定位：Rust 实现的新一代 pub/sub，**可 P2P 直连，无需 broker**
- 传输：默认 TCP（可配 UDP / 共享内存等）；本次为其默认配置
- 关键机制：endpoint 直连，无中心转发节点；传输与调度在 Rust runtime 内完成
- 对性能的影响：
  - 无中继 → 中小消息、多发布者场景下延迟与 CPU 具备优势
  - 内存开销结构性偏高（runtime + 缓冲策略）
  - 小包高频路径的每包调度开销需实测确认

## 第 7 页 · 原理（4）DDS

- 定位：以数据为中心的 RTPS 协议栈（本次为 Fast DDS 3.6.2）
- 传输：本次用 **UDPv4 + reliable**（显式指定，不与共享内存混测）
- 关键机制：自动发现（discovery）、丰富 QoS（reliability / durability / history depth / flow controller / max_blocking_time）
- 测量链：`Python → Fast DDS Python binding → Fast DDS C++ → UDP`
- 对性能的影响：QoS 配置（history depth、flow controller、publish mode）对高负载表现影响显著，需要与其它三家在同一负载档位下对齐参数

# 四、原理横向对比

## 第 8 页 · 原理横向对比表

| | VSOA | MQTT | Zenoh | DDS |
|---|---|---|---|---|
| 实现语言 / 形态 | C++ + Python 绑定 | C broker + Python 客户端 | **Rust** | C++ + Python 绑定 |
| 通信拓扑 | 直连（需 Position 服务） | **broker 中继（两跳）** | **P2P 直连** | 直连（自动发现） |
| 传输（本次） | TCP | TCP | 默认（TCP） | **UDPv4 / reliable** |
| 发现机制 | Position 服务 | broker 会话 | endpoint 直配 | **自动发现** |
| 大消息策略 | **应用层分片 60000 B** | broker 整体转发 | 原生传输 | RTPS 分片 |
| QoS 丰富度 | 少 | QoS 0/1/2 | 优先级 / 可靠性 | **最丰富** |
| 中心节点 | 有（Position，仅发现） | **有（broker，数据转发）** | 无 | 无 |

**这一页的作用**：后面所有实测差异，都要能在这张表里找到对应的机理线索（拓扑、分片、中心节点）。

# 五、测试方案

## 第 9 页 · 测试方案（1）：场景矩阵

- 8 个场景，每个 4–6 个档位；**每个场景只动一个影响因子**，拓扑固定为 1 发布者 / 1 订阅者（拓扑类场景除外）

| 场景 | 影响因子 | 档位 | 主要指标 |
|---|---|---|---|
| S01 点对点低延迟 | 发送速率 | 100 / 500 / 1000 / 2000 Hz | 延迟、P95、P99 |
| S02 消息大小扫描 | payload | 1 / 4 / 16 / **32** / **48** / 64 KiB | 延迟、吞吐、丢包 |
| S03 大消息吞吐 | payload | 64 / 128 / 256 / 512 KiB@20 Hz + **1 MiB@5 Hz** | 吞吐、P95、P99 |
| S04 发送速率扫描 | 发送速率 | 100 / 1000 / 5000 / 10000 Hz | 达成率、P99 |
| S05 一对多扇出 | 订阅者数 | 1 / 2 / 3 / 4 | 交付、资源 |
| S06 多对一汇聚 | 发布者数 | 1 / 2 / 3 / 4 | 交付、CPU |
| S07 多对多并发 | P×S | 1×1 … 4×4 | 吞吐、资源 |
| S08 长时间稳定性 | 持续负载 | 4 档 × 100 s | 漂移、内存 |

- 场景设计对齐需求文档 S01–S08；四家使用**完全相同的参数组**，便于横向并表

## 第 10 页 · 测试方案（2）：统一指标口径

**符号**：`S`=payload 字节；`N_sent` / `N_recv`=发出条数 / 去重后收到条数；`P`=订阅者数；`E = N_sent × P`；`T_delivery`=交付窗口

| # | 指标 | 公式 |
|---|---|---|
| U-1 | 单程延迟 | `(a_i − s_i) / 1e6`（两端同一时基） |
| U-2 / U-3 | 均值 / 分位数 | `mean(d)`；`h=(n−1)k` 线性插值 |
| U-4 | 标准差 | `pstdev`（总体标准差，ddof=0） |
| U-5 | 抖动 | `mean(\|d_i − d_{i−1}\|)`，仅取相邻序号 |
| U-6 / U-7 | 达成吞吐 / 应发吞吐 | `N × S × 8 / 窗口 / 1e6` |
| U-8 | 丢包率 | `(E − N_recv) / E` |
| U-9 | **达成率**（派生） | 达成吞吐 ÷ 应发吞吐 |

**统一硬约束**
- 吞吐一律按**净荷**计（不含协议头，不折算重传），一律用十进制 `1e6`
- `warmup` 不计入统计；`drain = 2.0 s` 单独用于收尾在途消息，不计入统计、也不计入丢包
- 一律取**去重后**计数
- 四家共用同一套实现：`mqtt/mqtt_metrics.py`（Unified metric definitions 1.0）

## 第 11 页 · 测试方案（3）：执行与数据规模

**环境**：本机回环，Windows，16 逻辑核；四家使用同一解释器与同一参数集

**数据规模**：VSOA / MQTT / Zenoh 各 35 组，DDS 32 组

**执行参数**

| 项 | 取值 | 说明 |
|---|---|---|
| 拓扑 | 1P/1S（拓扑类场景除外） | 保证单变量 |
| `warmup_seconds` | 1.0 | 不计入统计 |
| `drain_seconds` | 2.0 | **四家统一**，避免尾部在途消息被误记 |
| S08 时长 | 100 s / 档 | 四档覆盖轻到重负载 |
| 运行方式 | 统一入口批量执行，结果按组落盘 | 每组结果带参数指纹，支持断点续跑 |

**数据校验方式**
- 只采信 `status = completed` 的组；未完成的组以重跑补齐
- 每组结果落盘时记录完整参数与指标，可回溯到原始逐样本

# 六、测试结论

## 第 12 页 · 结论（1）：延迟水平与可重复性【图 1】

- 配图：`compare_repeatability.png`
- 方法：6 个场景中都存在一个**参数完全相同**的条件（1P/1S、1 KiB、1000 Hz）→ 同一条件被独立测 6 次，构成天然的多场景交叉验证

| 场景-组 | VSOA | MQTT | Zenoh |
|---|---|---|---|
| S01-3 | 0.1563 | 0.2092 | 0.2153 |
| S04-2 | 0.1460 | 0.2099 | 0.2526 |
| S05-1 | 0.1547 | 0.2303 | 0.2601 |
| S06-1 | 0.1424 | 0.2073 | 0.2720 |
| S07-1 | 0.1476 | 0.2153 | 0.2911 |
| S08-2 | 0.1481 | 0.2197 | 0.2813 |

**结论**
- 排序在 **6 个场景中完全一致**：`VSOA < MQTT < Zenoh`
- 均值极差：VSOA **9.3%** / MQTT 10.7% / Zenoh 28.9%
- 尾部（P99）极差：VSOA 38.0% / MQTT **13.1%** / Zenoh **127.6%**
- → **VSOA 延迟水平最低且重复性最好；MQTT 的尾部最稳定；Zenoh 的离散度最大**

## 第 13 页 · 结论（2）：消息大小阶梯与分片拐点【图 2】

- 配图：`compare_S02_payload_knee.png`
- 竖向虚线 = VSOA 分片阈值 **60000 B**：48 KiB 不分片，64 KiB 起切成 2 片

| 48 → 64 KiB（@100 Hz） | 均值 | P95 | P99 |
|---|---|---|---|
| VSOA | 0.516 → 0.759 ms（**+47%**） | +62% | **+70%** |
| MQTT | 1.001 → 1.383 ms（+38%） | — | 1.51 → 11.33 ms（**×7.5**） |
| Zenoh | 0.934 → 0.955 ms（**+2%**） | — | 无跳变 |

**结论**
- VSOA 与 MQTT **在同一位置出现跳变**：分别对应 VSOA 的应用层分片、MQTT 的 broker 转发大消息
- Zenoh 在同一区间基本无变化，与其"无中心、原生传输"的机理一致
- 这一段是**机制切换点**：从 48 KiB 到 64 KiB 不是量变而是路径切换

## 第 14 页 · 结论（3）：大消息的尾部代价【图 3】

- 配图：`compare_S03_large_message_tail.png`
- 核心指标 **P99 ÷ P95**：衡量"尾部被拉长了几倍"

| 1 MiB @5 Hz | 均值 | P95 | P99 | **P99÷P95** |
|---|---|---|---|---|
| VSOA | 4.26 ms | 5.03 | **17.29** | **3.44** |
| MQTT | 8.98 ms | 19.16 | 29.60 | 1.55 |
| Zenoh | 3.45 ms | 4.07 | 4.44 | **1.09** |

**结论**
- VSOA 的尾部分化最明显：1 MiB = **18 个分片**，整包延迟取决于最慢的一片
- Zenoh 尾部最平（1.09），均值也最低
- 吞吐方面：四档 20 Hz 下逐档等于目标值（10.5 / 21.1 / 42.1 / 84.3 Mbps），四家一致

## 第 15 页 · 结论（4）：拓扑成本结构【图 4】

- 配图：`compare_S05_S07_topology.png`
- 扇出(1P→N×S) / 汇聚(N×P→1S) / 并发(P×S) × 延迟 / 内存 / CPU

**结论**
1. **吞吐在所有拓扑下都逐档等于 `payload × 8 × 速率 × P × S`**（实测误差 <1%）→ 交付完整，吞吐由参数决定而非实现差异
2. **MQTT 扇出时 CPU 涨幅最大**（80.7% → 110.0%，+36%），另两家几乎不变 → 与 broker 中心化转发的机理一致
3. **Zenoh 内存恒为最高**（同档 220 MB vs 168 / 174 MB），与其 runtime 与缓冲策略一致
4. 延迟对拓扑规模弱敏感：端数从 1 扩到 4，延迟仅涨 10%–31%，而吞吐涨 16 倍

## 第 16 页 · 结论（5）：长时间稳定性与漂移【图 6】

- 配图：`compare_S08_drift.png`（S08 组2 = 1 KiB @1000 Hz，100 s，按 10 s 分桶）

| | 漂移（后 1/3 桶均值 vs 前 1/3 桶均值） | 样本数 | 解读 |
|---|---|---|---|
| VSOA | **+2.9%** | 99954 | 全程平稳，P95 接近一条直线 |
| MQTT | **−1.6%** | 99888 | 全程平稳 |
| Zenoh | **−18.6%** | 100000 | t≈25 s 前存在启动瞬态，P95 峰值 1.2 ms 后回落至 0.37 ms |

**结论**
- 三家在 100 s 持续负载下均无劣化趋势
- 差异体现在**进入稳态所需的时间**：VSOA / MQTT 从一开始即稳定，Zenoh 需要约 25 s 完成预热
- VSOA 的 P95 波动最小（全程约 0.21 ms 一条直线），Zenoh 的每桶峰值波动最大

## 第 17 页 · 结论汇总

**四条可横向引用的结论**

| # | 结论 | 支撑 |
|---|---|---|
| 1 | 延迟排序稳定：`VSOA < MQTT < Zenoh` | 6 个场景交叉验证一致 |
| 2 | VSOA 存在明确的机制切换点（48→64 KiB，均值 +47%、P99 +70%） | S02 六档阶梯，四家同参数 |
| 3 | 大消息尾部代价：VSOA 最重（P99÷P95=3.44）、MQTT 次之（1.55）、Zenoh 最轻（1.09） | S03 五档，机理对应分片数 |
| 4 | 内存开销：Zenoh 结构性偏高；CPU：MQTT 在扇出时涨幅最大 | 拓扑类场景三组一致 |
